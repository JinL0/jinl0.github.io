How the Digital Twins product map is built

A three-stage pipeline (crawl → extract → merge) turns public product pages into a small JSON catalog. A static site then renders that catalog with animations. No backend, no database, and every summary on the site can be traced to a source page.

1. Summary

  • Crawl: Playwright drives headless Chromium over public pages ( characters). It renders JavaScript, honors robots.txt, waits 1.5 s between requests, and discovers links one hop from 9 seed pages.
  • Extract: Claude () reads each page and returns JSON that matches a Pydantic schema through structured outputs. Every product record must include verbatim evidence quotes, and code checks that each quote appears in the page.
  • Merge: a deterministic Python step (no LLM) canonicalizes names, dedupes across pages, votes on categories, and keeps only dependency edges between products in the catalog.
  • Publish: hand-written HTML, CSS and JavaScript on GitHub Pages fetch data/products.json and render the stack diagram, catalog and canvas animation.

3. Architecture

Each stage reads the previous stage's file and writes its own, so any stage can be re-run alone. Re-merging after an alias fix costs nothing because it doesn't call the LLM. JSON Lines files are easy to diff, grep and stream, and they are enough at this size (tens of pages). A queue or database would add moving parts without solving a real problem.

4. Stage 1: Crawl with Playwright

Why a real browser? Product pages on nvidia.com build much of their content with JavaScript. A plain HTTP GET often returns a shell page, so Playwright renders the page in headless Chromium and reads the DOM after it loads.

# scrape.py (core of fetch)
resp = await page.goto(url, wait_until="domcontentloaded", timeout=45_000)
await page.wait_for_load_state("networkidle", timeout=8_000)   # best effort
text = await page.evaluate("""() => {
    const root = document.querySelector('main') || document.body;
    const clone = root.cloneNode(true);
    clone.querySelectorAll('nav, footer, header, script, style, [role=dialog]').forEach(n => n.remove());
    return clone.innerText; }""")
  • Scope control: 9 hand-picked seeds plus one hop of discovery. A discovered link is followed only if it stays on nvidia.com (/en-us/) or developer.nvidia.com, its path matches a topic list (digital-twin|omniverse|blueprint|isaac|cosmos|dsx|…), and it isn't news, a blog, events or a binary file. A hard cap (--max 30) bounds cost.
  • Cleaning: nav bars, footers and cookie dialogs are removed before reading innerText. Without this, every page "mentions" every product in the mega-menu, and the extractor over-reports.
  • Dedupe and redirects: URLs are normalized (fragment dropped, trailing slash), and the URL after redirects is stored. For example, /omniverse/digital-twins/ redirects to the glossary page, so that page is kept only once.
  • Change detection: each page stores a sha256 of its text, so a scheduled refresh can skip unchanged pages before calling the LLM.

5. Stage 2: Extract with Claude

Each page is one request. The response must match a Pydantic schema, and the SDK's messages.parse() sends it as a JSON schema through structured outputs. Output that doesn't match the schema can't be generated, so the code needs no JSON-repair or retry-on-parse-error logic.

# extract.py
class Product(BaseModel):
    name: str                 # official name as written on the page
    family: Family            # enum: Platform, Simulation, World foundation models, ...
    one_liner: str
    what_it_does: str         # own words, not copied marketing text
    digital_twin_role: str
    capabilities: list[str]
    industries: list[str]
    builds_on: list[str]      # -> dependency edges
    evidence: list[str]       # 2-4 quotes copied EXACTLY from the page

response = client.messages.parse(model="", max_tokens=16000,
    output_config={"effort": "medium"}, system=SYSTEM,
    messages=[{"role": "user", "content": f"<page url=… title=…>{text}</page>"}],
    output_format=PageExtraction)

The grounding check

A schema guarantees the shape of the answer, not whether it's true. Each record therefore has to cite the page. After the response arrives, ground() normalizes whitespace and case, then string-searches every evidence quote in the page text. Quotes that aren't found are removed, and a product left with no verified quote is dropped entirely. The check is cheap and deterministic, and it catches the most common failure: a product the model "knows about" but this page never describes.

def ground(extraction, page_text):
    haystack = norm(page_text)
    for p in extraction.products:
        good = [q for q in p.evidence if norm(q) in haystack]
        if good: kept.append({**p.model_dump(), "evidence": good})
  • Prompt rules that mattered: only products the page describes (not ones it merely links to), official names, summaries in the model's own words (to avoid republishing marketing copy), and quotes copied character for character.
  • Throughput and errors: 4 worker threads, and the SDK retries 429 and 5xx errors with backoff (max_retries=4). Auth and bad-request errors stop the run immediately. Any other per-page failure is logged and doesn't kill the batch.
  • Cost: this run used input and output tokens, about at list price.

6. Stage 3: Merge deterministically

Popular products appear on many pages under slightly different names ("NVIDIA Isaac Sim", "Isaac Sim™"). Merging uses plain Python on purpose: it is free to re-run, gives the same output every time, and is easy to debug.

  1. Canonical key: strip ™/®/©, a leading "NVIDIA", case and whitespace, then apply a small hand-maintained ALIASES map (e.g. "universal scene description" → "openusd"). The alias map grows by reading each run's output: human review where it's cheap.
  2. Resolve fields: family is a majority vote. Summary text comes from the best record, preferring the product's own page and then the most verified quotes. Capabilities and industries are a frequency-ranked union, capped at 6 and 8.
  3. Edges: builds_on names are canonicalized too. An edge is kept only if both ends are in the catalog, so the stack diagram never points at a node that doesn't exist.

7. Frontend: HTML, CSS and JavaScript, no framework

The site is two HTML files, one stylesheet and two scripts, served by GitHub Pages as-is. Without a build step, the repo deploys on every push and will still work in five years.

  • Hero animation: a single function state(t) computes the conveyor offset, arm angles and the number of boxes placed. The same scene function draws it three times: solid (physical), wireframe (twin), and dashed at t + 350 ms (the twin's prediction). That is the core idea of a digital twin, shown in about 150 lines of Canvas 2D. The loop pauses when the canvas scrolls off-screen (IntersectionObserver) and renders one still frame for users who prefer reduced motion.
  • Dependency tracing: hovering over a pill measures pill positions with getBoundingClientRect and draws cubic Bézier curves in an SVG overlay, with an animated stroke-dashoffset. Unrelated pills fade out.
  • Color: eight product families use a fixed-order categorical palette, validated on the dark surface (worst adjacent colorblind ΔE 8.4, every color ≥ 3:1 contrast). Color always appears with a text label and is never the only cue. NVIDIA green is used only for UI accents, never for data.
  • Accessibility: cards and pills are real <button>s, the drawer is a native <dialog> (focus trap and Esc for free), the canvas has a text description, and all user and page text is escaped before insertion.

8. Quality & evaluation

  • Automatic: verified-quote rate, and the number of product records dropped for having no verified quote (above). A sudden fall in the verified-quote rate after a page redesign is the signal to check the crawler's text cleaning.
  • Manual: after each run, spot-check about 10 products against their source pages for wrong category, wrong dependency, or a summary that overstates the page. Fixes go into ALIASES or the prompt rules, never hand-edited JSON.
  • Known limits: a verified quote proves the page says something about the product, not that every summary sentence is supported. Dependencies are only as complete as the pages that state them. One-hop crawling misses products with no link from the seeds.

9. Responsible scraping

  • Python's urllib.robotparser checks robots.txt before every request. One browser tab, a 1.5 s delay between requests, and a descriptive user agent with a contact URL.
  • Raw page text stays local (raw/ is git-ignored). The site publishes only short machine-written summaries with links back to nvidia.com.
  • Clearly labeled as unofficial; product names are NVIDIA trademarks; no NVIDIA logos or images are used.

10. Trade-offs & alternatives considered

DecisionChosenAlternativeWhy
FetchingPlaywright (headless Chromium)requests + BeautifulSoupPages render content with JavaScript; a browser sees what users see. It costs about 1–3 s per page, which is fine at this scale.
ExtractionLLM + JSON schemaCSS selectors per templatePages use many different templates, and selectors break when a page is redesigned. The LLM also writes the summaries.
Hallucination controlVerbatim evidence + string matchA second LLM call as judgeDeterministic and free. An LLM judge is a good next layer for checking summary faithfulness.
MergeRules + alias mapLLM entity resolution / embeddingsAbout 40 entities: rules are reproducible and reviewable. Switch to embeddings if the catalog grows 10×.
StorageJSON Lines filesSQLite / PostgresTens of records, with diffs in git. A database is worth it with history and incremental refresh.
FrontendVanilla JS, SVG, CanvasReact + D3 / Three.jsNo build step, fast load, and small enough to read in one sitting.

11. Next steps

  • Scheduled refresh: a monthly GitHub Action runs the crawl, skips pages whose sha256 hasn't changed, extracts the rest, re-merges, and opens a PR showing the JSON diff for review.
  • Eval set: about 20 hand-labeled pages (expected products, families and edges) to measure precision and recall when the prompt or model changes.
  • Faithfulness judge: a second pass that checks each summary sentence against the page and flags anything it can't support.
  • 3D: render the hero cell from a small OpenUSD file with three.js, so the twin is described by the same scene format it explains.

12. Reproduce

cd nvdadigitaltwins/pipeline
uv venv .venv --python 3.12 && uv pip install --python .venv/bin/python -r requirements.txt
.venv/bin/python -m playwright install chromium

.venv/bin/python scrape.py --max 30        # → raw/pages.jsonl       (~2 min)
export ANTHROPIC_API_KEY=...               # personal key
.venv/bin/python extract.py                # → raw/extractions.jsonl (~3 min)
.venv/bin/python merge.py                  # → ../data/products.json

cd .. && python3 -m http.server 8000      # preview at http://localhost:8000
